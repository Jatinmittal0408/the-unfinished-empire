# AI Cinematic Edition V1.1: cinematic playback repair

> Engineering report, kept as written during development. Branch, tag and commit references point to the original
> development repository. Its measurements used the approved master files; this repository ships web encodes with
> identical frame structure, re-verified as described in [`MEDIA.md`](MEDIA.md) and [`VERIFICATION.md`](VERIFICATION.md).

- **Branch:** `ai-cinematic-edition`. The V1 checkpoint is tag `v1-checkpoint` (= `925fbd4`, unchanged).
- **Unchanged:** the visual design, typography, courtyard interface and approved footage. No new media was generated, and Blender was not used.
- **Measured on:** Apple M5 Pro, 120 Hz display, Chrome for Testing 147 (headed, hardware decode). All runs used production builds (`vite build` + `vite preview`) on a clean GPU unless stated otherwise.

## 1. What changed, finding by finding

| # | V1 finding | V1.1 change |
|---|---|---|
| 1 | Two playing videos blended on screen → compositor collapse | **No edit ever shows two moving videos.** The incoming clip is parked *under* the outgoing layer, paused on a decoded frame, and started while still covered. It is exposed in the frame callback of its first *steady* presented frame. In that same rendering update the outgoing layer is either hidden (cut) or replaced by a *held copy of the frame on screen* (dissolve / threshold). The held copy is a static WebGL canvas, pre-compiled at idle, that clears over the one playing clip. A per-frame sampler confirms at most one visible playing video in every run |
| 2 | Exterior → gateway: 1.25 s, 14 % zoom on a frozen frame | **The push is removed.** The edit is now a 0.5 s dissolve from the held aerial frame (no zoom) into the gateway approach, which is already moving. The title starts clearing about 6 ms after the click. A straight cut and a dark-first variant are also available |
| 3 | Gateway → courtyard began 0.6 s before the gateway ended but lasted 0.95 s → freeze | **The gateway → courtyard edit is a doorway match cut chosen from decoded frames:** gateway frame 189 → courtyard frame 8. The gateway never reaches its end, nothing simulates its motion, and a backstop cuts anyway if the outgoing clip ever passes frame 189 |
| 4 | Joins waited on `play()` resolving | **Every reveal is gated on `requestVideoFrameCallback`.** Parking waits for the parked frame to be presented, and the incoming clip is exposed only after two consecutive source frames are presented back to back. Without the API, a rAF poll of `currentTime` plus `seeked`/`readyState` is used instead |
| 5 | Replay/navigation races | **Every command runs as a cancellable `Seq`.** Each await is wrapped so cancellation settles the sequence immediately (no pending promises); animations and timers are stopped; and clips the new scene doesn't use are released. Replay is now one sequence, so Esc, Skip, Back or a room cancels it as a whole. Double Enter is ignored. **Seen policy:** the entrance counts as seen as soon as Enter starts it |

## 2. Choosing the edits

Edit points were taken from the decoded frames (`npm run analyse:joins`, contact sheets in `.generated/joins/`).

- **Gateway → courtyard.**
  - The gateway ends on a slow push (≈0.3 %/frame) towards closed doors, centred.
  - Courtyard frames 0–8 face a closed door, also centred and slightly larger, on a similar slow push (≈0.6 %/frame).
  - The courtyard doors then open (8–24) and the camera passes through a dark passage (40–70).
  - Cutting gateway 189 → courtyard 8 is an axial "cut-in": door to larger door, which begins to open as the visitor moves through. Forward motion continues across the cut.
- **Exterior → gateway.** This is a new shot (aerial establishing → ground-level arrival). Within the picture area the exposure is close: mean luminance ≈96 against 104. The real difference is colour temperature (amber dusk sky → blue sky). Following the brief, no grading was applied.
- **Start-up compensation.** A clip started *under another playing clip* takes about 300 ms to present steadily: its first frames arrive late and catch up (1 → 4 → 7 → 8). It is therefore parked on frame 1 and started 7 gateway frames before the cut. Measured over 8 production runs: the cut lands on gateway 189 → courtyard 8 every time, with 0 skipped frames after the cut.

**Candidates benchmarked** (all with one visible moving video):

| | cut | held-frame dissolve | dark-first threshold |
|---|---|---|---|
| Exterior → gateway | Clean cut, but the still homepage jumps straight into motion | **Default.** 0.5 s; the movement emerges as the aerial clears. Amber and blue skies overlap briefly | 0.7 s; ragged sky patches appear through the façade's shadows (reads as a glitchy luma key) |
| Gateway → courtyard | **Default.** Door → larger door that opens: the clearest | 0.33 s; superimposes two different arches (ghosting) | 0.5 s; breaks the door up |

The defaults were chosen by eye from the side-by-side captures. Passing tests does not make an edit cinematic, so please judge them in the harness (`/harness.html`), which plays the recordings and opens any of the 9 combinations live.

## 6. Problems found and fixed during this work

- **The held-frame edits revealed the wrong picture.** The first dissolve/threshold implementation cleared the held frame onto the outgoing layer's own still/poster underlay instead of the incoming clip. The layer-state metrics counted these joins as clean; the side-by-side contact sheets showed the error. Every other picture in the outgoing layer is now hidden once the held frame takes over. Lesson recorded: the edits are checked visually, not only by metrics.
- **A paused `<video>` fading over a playing clip still dropped frames** (rAF up to 34 ms, 1–2 skipped). This is why the held frame is a static canvas.
- **Creating the WebGL context at the cut** caused one 80–100 ms stall on the first threshold edit. It is now created and compiled at idle.
- **Skip briefly became a hard cut,** because the parked courtyard counted as "already on screen". The still logic now also requires the layer to be on top.
- **V1 packaging defect.** The app's `.gitignore` line `media` (meant for the local video folder) also matched `src/media/`. So `src/media/scenes.ts` and `src/media/manifest.json` were **never committed in V1**, and they were missing from the V1 review ZIP. Fixed: the rule is now `/media`, and both files are committed in V1.1. The V1 baseline used for the benchmarks was rebuilt from `v1-checkpoint` with `scenes.ts` reconstructed (the join block from V1). Its bundle matches the original V1 build exactly (301.36 kB).

## 7. Remaining visual issues, and where regenerated footage would help

These belong to the footage, not the engine.

1. **Exterior → gateway is still a change of world:** amber dusk aerial to blue-sky ground level, and a gate that isn't the one visible on the exterior. The dissolve makes the change gentle but doesn't remove it. **Regeneration would help most here:** a gateway clip at the exterior's golden hour, or one that starts from the exterior's last frame (image-to-video), would allow a true continuation.
2. **The gateway → courtyard cut joins two different gates** (pointed arch → cusped arch with chhatris). It reads as a cut-in, but frame by frame it is a different building. A courtyard clip that opens on the gateway's own doors would make it seamless.
3. **The homepage is a still** (the held exterior), so any entrance starts from rest. The dissolve lets motion emerge rather than snap. A gently moving homepage loop would need new footage.
4. **The courtyard's own first 8 frames are skipped** by the cut. They are a near-static door, so nothing important is lost.
5. **Not tested here:** Safari and Firefox (the rVFC fallback path is implemented but unmeasured), phones' real hardware, and a GPU under load. The ≈300 ms covered start-up was measured on this machine; elsewhere the backstop keeps the outgoing clip from freezing, but the cut frame may shift by a few frames.
6. **The recordings are CDP screencasts** (≈30–90 composited frames per second, timestamped), resampled to 30 fps. They show the edits faithfully but are not a frame-exact 120 Hz capture.
